## Deploy the disposable staging stack

The commands below use the current repository layout. For the checks that run on the host, install the package with `python -m pip install -e . --no-deps` and its optional dependencies with `python -m pip install -r requirements.txt`. From the repository root, on a host with a working Docker Linux engine:

```text
docker compose -f deploy/staging.yaml up --build -d
python scripts/checks/wait_ready.py
```

Open `http://127.0.0.1:8766`. Select the synthetic workspace. The PostgreSQL alias is `customer-lab`. The staging email inbox is at `http://127.0.0.1:8025`. The initial plan used MinIO; the tested staging profile now uses Moto at `http://127.0.0.1:9900` and has no object-store console.

The staging credentials in `deploy/staging.yaml` and `deploy/staging-init.sql` are deliberately public test fixtures, bound to loopback. Do not deploy this file publicly or import confidential data into this disposable lab. It explicitly disables production-only TLS requirements and enables demo sign-in.

Enable the live acceptance tests only against that disposable stack:

```powershell
$env:RECON_RUN_INTEGRATION = '1'
python -m unittest discover -s tests -p test_integration.py -v
```

The tests verify that the source role cannot update data, that job ownership is fenced, and that a real database comparison passes through remote workers. The SQL fixture has 125 injected findings; the CSV fixture separately includes 25 invalid dates and therefore has 150. These different expected totals are intentional.

## Production configuration

Use the production compose.yaml, not the disposable staging file. It requires independent session and MFA encryption secrets, defaults to mandatory native MFA, and enforces dataset permissions. Bootstrap administrator credentials apply only to a fresh production data volume.

Optional overlays:

```text
docker compose -f compose.yaml -f deploy/distributed.yaml up --build -d
docker compose -f compose.yaml -f deploy/sso.yaml up --build -d
docker compose -f compose.yaml -f monitoring/compose.yaml up --build -d
```

Overlays can be combined after reviewing their required environment values. Remote workers need a private artifact bucket, workload identity permissions and a PostgreSQL job database with verified TLS. Initialize the job schema once, using a migration identity:

```text
python -m reconcile.distributed --migrate
```

Runtime broker identities can then be limited to SELECT/INSERT/UPDATE on reconcile_jobs. Runtime workers do not run DDL unless RECON_JOB_MIGRATE=1 or the explicit local-stage flag is enabled. Artifact access needs bucket listing plus object read/write; prefer workload IAM roles over static keys. Use an appropriate object lifecycle policy for expired intermediate artifacts.

The dashboard still has **one application/coordinator process and a persistent local SQLite metadata volume**. Multiple remote comparison workers are supported by the new adapter. Multiple dashboard replicas and automatic failover of the dashboard store are not implemented. If your availability requirements demand those, a separate migration of application metadata and coordinated audit writes is required. No single-host package can establish your organization's availability target without deployment and recovery testing.

## Identity and recovery

Set RECON_MFA_KEY to a stable random secret independent of RECON_SECRET. Rotating the session secret invalidates sessions and recovery links; preserve the MFA key so authenticator seeds remain decryptable. One-use recovery codes are stored as hashes, not plaintext.

OIDC configuration requires issuer, client ID, client secret, approved email domain, callback URL and a trusted-proxy secret. Pre-provision members in the application. Apply required MFA/conditional-access policies at the identity provider when SSO-only mode is used. The app does not infer administrator roles from untrusted identity headers or allow arbitrary auto-provisioning.

SMTP configuration requires RECON_SMTP_HOST, RECON_SMTP_PORT, RECON_SMTP_FROM, and optionally RECON_SMTP_USER/RECON_SMTP_PASSWORD. Production uses verified STARTTLS. Recovery links are queued in an encrypted outbox, delivered by a separate thread and retried at most three times. No real notification or recovery email was sent while building this release. The staging Mailpit configuration captures mail locally instead.

Database connection aliases used by non-admins must declare a `dataset` field matching the requested dataset. Grant write access to that dataset before allowing analysts to run the alias. This prevents creating a new dataset name to bypass permissions on an existing source.

## Governance procedures

Generate and separately escrow a base64-encoded 32-byte RECON_ARCHIVE_KEY. It is independent of session and MFA keys. Keep archives outside the application data volume.

```text
python -m reconcile.manage --data-dir /data retention --archive-dir /independent-archive --days 90
python -m reconcile.manage --data-dir /data archive-audit --archive-dir /independent-archive --days 365
python -m reconcile.manage --data-dir /data verify-audit --trusted-head TRUSTED_ARCHIVED_HEAD
```

Retention is a dry run unless `--apply` is present. Stop the application/coordinator and workers for retention maintenance; the tool requires exclusive coordinator ownership. Legal holds prevent processing. `--purge` is a separate explicit option. It removes application business keys, source/destination values, review notes and snapshots only after a verified encrypted archive is made. By default, production also requires a successful independent compliance-mode object-lock copy before purge.

Configure RECON_ARCHIVE_S3_BUCKET and RECON_ARCHIVE_KMS_KEY for the locked copy. The bucket must already have Object Lock enabled. The recorded object version, local archive SHA-256 and audit checkpoint provide independent evidence. COMPLIANCE retention is irreversible until its expiry; choose the policy with your records owner before enabling it. Single-object archive uploads are currently limited to 5 GiB.

Restore/decrypt does not require a surviving application database:

```text
python -m reconcile.manage decrypt-archive evidence.recon recovered.zip
```

Only a verified plaintext ZIP is promoted to the requested output. Keep the recovered evidence protected. Full application backup/restore remains available through `python -m reconcile.manage backup` and the [operations guide](../operations.md). Governed archives are independent and are not silently bundled into the application backup.

Master audit records are not purged by run retention. New review audit events contain a note hash, while the review text lives in the governed run evidence. Older audit events created before this release may contain full note text. Apply a separate audit retention policy; this package does not claim regulatory certification or guaranteed deletion of every possible user-entered identifier.

## Updated operating limits

| Resource | Default |
|---|---:|
| Browser upload chunk | 1 MiB |
| Sealed snapshot | 1 GiB |
| Temporary upload quota per user | 4 GiB |
| Temporary upload lifetime | 24 hours |
| Records per snapshot | 5,000,000 |
| Findings per run | 2,000,000 |
| Pending/running comparisons | 10 |
| Remote artifact upload for a governed archive | 5 GiB |

Large exports use temporary disk files and streamed responses. Excel splits into additional sheets at its row limit; cells beyond Excel's text limit explicitly direct the analyst to CSV. The inline JSON CSV interface remains limited to 12 MiB per snapshot; the browser uses the larger chunked interface. Size ceilings are guardrails, not measured capacity claims. Tune them only after representative row-width, exception-density, disk and runtime tests. Worker scratch space is disk-backed rather than an unbounded RAM filesystem.

## Validation still requiring an environment

At the initial release-candidate checkpoint, Docker Desktop was present but no reachable Linux engine became available after startup attempts. No container image, live PostgreSQL job lease, MinIO round trip or OIDC callback was counted as verified at that checkpoint, and the three integration tests were explicit skips. Subsequent container, PostgreSQL/Moto worker, HTTPS and local SMTP checks passed, as recorded in the [final deployment checks](../validation/2026-10-29/deployment_readiness.json). Organization-specific OIDC remains an environment acceptance task. The CI workflow also runs integration, dependency and static security checks on Linux Docker runners.

Before a real rollout, check the pipeline for the commit being deployed, review the pinned image/dependency versions, configure your actual identities and notification destinations, rehearse restore on the target storage, and obtain an independent security review. Alertmanager has no external recipient by default. These are deployment and assurance gates, not results already obtained on this workstation.
